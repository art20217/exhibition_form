# 同步契約 v1

會談紀錄表的平板與伺服器之間的同步協定。

**這份文件是寫給實作伺服器的人看的。** 客戶端（`index.html`）已經照著這份契約準備好
資料模型；伺服器端目前不存在，日後由誰實作都可以，只要符合下面的規則。

> **狀態**：v3.12 完成了客戶端的資料模型（`updatedAt`、`deletedAt`、`deviceId`）。
> 同步引擎與端點呼叫**尚未實作**，預計在 v3.13。

---

## 為什麼是這些規則

三個環境條件決定了以下每一項設計，改動前請先確認條件沒變：

1. **展場的 Wi-Fi 有，但不穩。** 請求會在任何一個時間點斷掉，包括「伺服器已經寫入、
   但回應沒送到客戶端」這個最難處理的時刻。
2. **裝置是 iPad。** Safari 從未實作 Background Sync API（到 iOS 26.5 仍然沒有），
   所以同步只能在前景進行：app 啟動時、切回前景時、`online` 事件時。
   **伺服器不能假設客戶端會定期回報**，一台平板可能整天不出現。
3. **平板完全離線也必須能用。** 同步是附加能力，不是運作前提。

## 資料模型

每筆紀錄在客戶端長這樣（`upsertFlowRecord`）：

```jsonc
{
  "id": "9f1c…",              // UUID，由客戶端產生
  "eventId": "3a7b…",         // 所屬活動
  "deviceId": "c02e…",        // 產生這筆紀錄的裝置（UUID，非人工命名）
  "device": "Tablet-1",       // 人工標籤，可重複、可空白，僅供顯示
  "timestamp": "2026-09-23T01:12:33.000Z",  // 建立時間，不再改變
  "updatedAt": "2026-09-23T02:40:11.000Z",  // 最後修改時間
  "deletedAt": null,          // 非 null 即為墓碑
  "customerFields": { },      // 四組欄位值，鍵為欄位 id
  "needsFields": { },
  "companyFields": { },
  "staffFields": { },
  "gdprConsent": true,
  "cardPhoto": "data:image/jpeg;base64,…"   // 不走同步的 JSON，見下方
}
```

**欄位定義（`fieldDefinitions`）與活動（`events`）第一版不同步。** 每場活動的欄位是
在平板上各自設定的，紀錄裡存的是欄位 id 與選項的英文值，語意不依賴定義。伺服器如果
要還原成人類可讀的表格，需要另外收一份定義快照——這一項留給 v2。

## 端點

所有請求帶 `Authorization: Bearer <token>`，token 是**裝置層級**的，存在平板的系統設定裡。

> **後台的 4 位數 PIN 不是憑證。** 它是共用的、只防誤觸（README 已載明），
> 絕不可以拿來當 API 認證。

### `POST /v1/records`　推送

```jsonc
// 請求
{ "deviceId": "c02e…", "records": [ /* 上面的紀錄物件，不含 cardPhoto */ ] }

// 回應
{ "results": [ { "id": "9f1c…", "status": "accepted" },
               { "id": "4b20…", "status": "superseded",
                 "record": { /* 伺服器上較新的版本 */ } } ],
  "seq": 10428 }
```

**必須是冪等的。** 伺服器依 `id` upsert。同一批資料重送兩次的結果，必須和送一次完全
相同——這是不穩定 Wi-Fi 下最重要的一條：客戶端無法分辨「請求沒送到」和「回應沒回來」，
所以它會重送，而重送**不能**長出第二筆。

一批以 50 筆為上限。回應要逐筆給狀態，不要整批成功或整批失敗——一筆壞資料不該
擋住其他 49 筆。

### `GET /v1/records?since=<seq>&limit=<n>`　拉取

```jsonc
{ "records": [ /* 含墓碑 */ ], "seq": 10500, "hasMore": false }
```

`seq` 是**伺服器指派的單調遞增序號**，不是時間戳。

**不要用時間當游標。** 多台平板的時鐘不同步，展場平板也可能整天沒對時；用
`?since=<timestamp>` 會在時鐘偏差的時候靜靜漏掉資料，而且漏掉的那幾筆永遠不會再出現。

### `PUT /v1/photos/<recordId>`　名片照片

Body 是二進位 JPEG，`Content-Type: image/jpeg`。同樣冪等（同一個 `recordId` 覆蓋）。

**照片刻意不走紀錄的 JSON。** 壓縮後單張 200–500KB，100 筆就是 20–50MB。在斷斷續續的
Wi-Fi 下，把照片和紀錄綁在同一個請求裡代表：照片傳失敗會連帶讓紀錄也重傳，永遠傳不完。
分開之後，紀錄先到（那是真正重要的資料），照片可以慢慢補、單獨重試。

## 衝突處理

**Last-write-wins，比 `updatedAt`；相同時比 `deviceId` 字串大小**（純粹為了讓兩邊
算出同樣的贏家，沒有其他意義）。

**這個規則會丟掉一次編輯。** 如果兩台平板都改了同一筆而且都還沒同步，較早的那次修改
會被覆蓋且無法復原。接受的理由是：每筆紀錄由某一台平板建立，實務上也只有那台會編輯它
——接待人員修的是自己剛才填錯的東西。跨裝置同時編輯同一位訪客，在這個流程裡幾乎不會發生。

如果日後這個假設不成立（例如加了集中式的資料整理介面），這一條要重新設計，不要
硬撐 LWW。

### 墓碑

刪除是 `deletedAt` 非 null 的紀錄，一樣參與 LWW。伺服器**必須保留墓碑**，否則已刪除的
紀錄會從還沒同步的平板上重新長回來。

客戶端的墓碑只保留 `id` / `eventId` / `deviceId` / `timestamp` / `updatedAt` / `deletedAt`，
**所有欄位值與照片都已丟棄**——已刪除的紀錄不該還在平板上留著訪客的姓名、電話與名片照。

伺服器確認收到之後，客戶端可以清除本機墓碑。清除多久之後才安全，取決於「一台平板可能
多久沒上線」，建議至少保留一次展覽的長度。

## 個資與合規

**測試階段一律使用假資料。**

給訪客看的同意條文寫的是「本人資料不會提供予第三方」。上傳到**該公司自己的**伺服器
沒有問題（同一個資料控制者），但開發或測試用的伺服器**就是第三方**——把真實訪客資料
送上去會直接違反平板上剛給對方看過的那段文字。

同步一旦上線，安全性與合規（[#10](https://github.com/art20217/exhibition_form/issues/10)）
就不再是可以延後的項目：資料離開裝置的那一刻，「PIN 只防誤觸」會從已知限制變成真正的問題。

## 給實作者的檢查清單

- [ ] 同一批資料送兩次，結果與送一次相同（冪等）
- [ ] `seq` 單調遞增，且不因伺服器重啟而倒退
- [ ] 墓碑會被保留並回傳給拉取端
- [ ] 一筆壞資料不會讓整批失敗
- [ ] 照片端點與紀錄端點可以獨立失敗與重試
- [ ] 認證失敗回 401，不要回 200 加錯誤訊息（客戶端要能區分「網路壞了」和「憑證錯了」）
