# 同步契約 v3

會談紀錄表的平板與伺服器之間的同步協定。

**這份文件是寫給實作伺服器的人看的。** 客戶端（`index.html`）已經照著這份契約準備好
資料模型；伺服器端目前不存在，日後由誰實作都可以，只要符合下面的規則。

> **狀態**：紀錄（v3.13）、名片照片（v3.14）、活動與欄位定義（v3.15）、
> 一筆紀錄多張名片（v3.16）均已實作。
> 客戶端在 `index.html` 的 SYNC 區塊，伺服器端的參考實作在 [`server/`](../server/)。
>
> - **v2**：新增 `/v1/events` 端點（活動本身＋欄位定義快照）、活動的擁有者規則、活動墓碑。
> - **v3**：照片端點的路徑參數從**紀錄 id 改成照片 id**，紀錄新增 `photoIds` 欄位。
>   這是**破壞性變更**——正式伺服器還不存在，現在改最便宜。
>
> **路徑前綴一直是 `/v1`**，變的是端點集合與語意，不是傳輸格式。

---

## 為什麼是這些規則

三個環境條件決定了以下每一項設計，改動前請先確認條件沒變：

1. **展場的 Wi-Fi 有，但不穩。** 請求會在任何一個時間點斷掉，包括「伺服器已經寫入、
   但回應沒送到客戶端」這個最難處理的時刻。
2. **裝置是 iPad。** Safari 從未實作 Background Sync API（到 iOS 26.5 仍然沒有），
   所以同步只能在前景進行：app 啟動時、切回前景時、`online` 事件時。
   **伺服器不能假設客戶端會定期回報**，一台平板可能整天不出現。
3. **平板完全離線也必須能用。** 同步是附加能力，不是運作前提。

## 資料模型

每筆紀錄在客戶端長這樣（`upsertFlowRecord`）：

```jsonc
{
  "id": "9f1c…",              // UUID，由客戶端產生
  "eventId": "3a7b…",         // 所屬活動
  "deviceId": "c02e…",        // 產生這筆紀錄的裝置（UUID，非人工命名）
  "device": "Tablet-1",       // 人工標籤，可重複、可空白，僅供顯示
  "timestamp": "2026-09-23T01:12:33.000Z",  // 建立時間，不再改變
  "updatedAt": "2026-09-23T02:40:11.000Z",  // 最後修改時間
  "deletedAt": null,          // 非 null 即為墓碑
  "customerFields": { },      // 四組欄位值，鍵為欄位 id
  "needsFields": { },
  "companyFields": { },
  "staffFields": { },
  "gdprConsent": true,
  // 一張名片有正反面，所以是清單而不是單一值。每張帶自己的 id。
  "cardPhotos": [ { "id": "7d31…", "dataUrl": "data:image/jpeg;base64,…" } ]
}
```

活動在客戶端長這樣（`putEvent`）：

```jsonc
{
  "id": "3a7b…",              // UUID，由客戶端產生
  "name": "2026 秋季展",
  "startDate": "2026-09-23",  // 本地日期字串，非 UTC 時間戳，見下方
  "endDate": "2026-09-25",
  "status": "active",         // active | ended
  "staff": [ "王大明", … ],    // 接待人員名冊
  "ownerDeviceId": "c02e…",   // 只有這台可以改欄位定義
  "ownerDeviceName": "平板 A", // 人工標籤，供其他平板的唯讀說明顯示
  "createdAt": "2026-08-01T…",
  "updatedAt": "2026-09-23T…", // LWW 依據
  "deletedAt": null,           // 非 null 即為墓碑
  "fieldDefs": {               // 只在傳輸時夾帶，客戶端另存於 fieldDefinitions
    "customerFields": [ { "id": "name", "nameZh": "姓名", "type": "text", … } ],
    "needsFields": [ … ], "companyFields": [ … ], "staffFields": [ … ]
  }
}
```

**`startDate` / `endDate` 是本地日期字串，不要當成時間戳處理。** 展場在台灣（UTC+8），
把 `2026-09-23` 當午夜轉成 UTC 會變成前一天——這是真的發生過的錯（v3.11），
`tests/e2e-timezone.js` 現在守著它。

**紀錄本身不自我描述。** 紀錄存的是欄位 id 與選項的英文值；中文標籤、欄位型別、
後台自訂欄位的名稱都只存在於定義裡。匯出檔本來就附一張 `Field Definitions` 工作表，
理由完全相同。因此**定義快照隨活動一起送**：一個 `POST /v1/events` 的請求自我完備，
伺服器不必再去拼湊。

**活動要在紀錄之前同步。** 先有活動，拉回來的紀錄才有歸屬；反過來會有一段時間紀錄掛在
不存在的活動上，而那樣的紀錄**不出現在任何畫面、任何筆數、任何匯出**——每個讀取端都經過
`eventRecords()`，它只比對目前開啟的活動。

## 端點

所有請求帶 `Authorization: Bearer <token>`，token 是**裝置層級**的，存在平板的系統設定裡。

> **CORS 的 `OPTIONS` 必須在路由之前回答，包含你沒有實作的路徑。** App 由 GitHub Pages
> 提供，每一個同步請求都是跨來源的，所以瀏覽器會先送預檢。**若預檢被回 404，瀏覽器會
> 直接擋下請求，客戶端收到的是一個沒有狀態碼的網路錯誤**——它就分不出「這個端點不存在」
> 和「網路斷了」，也就無法像下面那樣降級。參考實作在檢查權杖之前就先回 204。

> **後台的 4 位數 PIN 不是憑證。** 它是共用的、只防誤觸（README 已載明），
> 絕不可以拿來當 API 認證。

### `POST /v1/records`　推送

```jsonc
// 請求
{ "deviceId": "c02e…", "records": [ /* 上面的紀錄物件，不含 cardPhotos，但帶 photoIds */ ] }

// 回應
{ "results": [ { "id": "9f1c…", "status": "accepted" },
               { "id": "4b20…", "status": "superseded",
                 "record": { /* 伺服器上較新的版本 */ } } ],
  "seq": 10428 }
```

**必須是冪等的。** 伺服器依 `id` upsert。同一批資料重送兩次的結果，必須和送一次完全
相同——這是不穩定 Wi-Fi 下最重要的一條：客戶端無法分辨「請求沒送到」和「回應沒回來」，
所以它會重送，而重送**不能**長出第二筆。

一批以 50 筆為上限。回應要逐筆給狀態，不要整批成功或整批失敗——一筆壞資料不該
擋住其他 49 筆。

### `GET /v1/records?since=<seq>&limit=<n>`　拉取

```jsonc
{ "records": [ /* 含墓碑 */ ], "seq": 10500, "hasMore": false }
```

`seq` 是**伺服器指派的單調遞增序號**，不是時間戳。

**不要用時間當游標。** 多台平板的時鐘不同步，展場平板也可能整天沒對時；用
`?since=<timestamp>` 會在時鐘偏差的時候靜靜漏掉資料，而且漏掉的那幾筆永遠不會再出現。

### `POST /v1/events`　推送活動與欄位定義

```jsonc
// 請求
{ "deviceId": "c02e…", "events": [ /* 上面的活動物件，含 fieldDefs */ ] }

// 回應
{ "results": [ { "id": "3a7b…", "status": "accepted" },
               { "id": "5c81…", "status": "accepted", "fieldDefsRejected": true },
               { "id": "9d02…", "status": "superseded",
                 "event": { /* 伺服器上較新的版本 */ } } ],
  "seq": 214 }
```

規則與 `/v1/records` 相同：冪等、逐筆結果、一批 50 筆為上限。

> **分階段實作是可以的。** 客戶端把活動端點的 **404 視為「這台伺服器還沒有這個功能」**：
> 它會記下來、這個工作階段內不再嘗試，然後**照常同步紀錄**，並在狀態列說明。所以先做
> `/v1/records`、之後再補 `/v1/events` 是一條可行的路徑——但**只有 404 有這個待遇**，
> 其他錯誤一律當成故障。

**非擁有者送來的 `fieldDefs` 要拒收，但活動本身照收**，並在該筆結果回
`fieldDefsRejected: true`。整批失敗是錯的——同一筆可能還帶著合法的狀態變更
（例如「結束活動」，任何平板都能做）。

### `GET /v1/events?since=<seq>&limit=<n>`　拉取活動

```jsonc
{ "events": [ /* 含墓碑，含 fieldDefs */ ], "seq": 260, "hasMore": false }
```

**活動的 `seq` 是獨立的序號空間**，與紀錄的互不干擾。客戶端分別記 `syncSeq` 與
`syncEventSeq`。共用一個序號會讓兩邊的分頁互相推擠，沒有任何好處。

### `PUT /v1/photos/<photoId>`　名片照片

Body 是二進位 JPEG，`Content-Type: image/jpeg`。同樣冪等（同一個 `photoId` 覆蓋）。

**路徑參數是照片 id，不是紀錄 id。** 一筆紀錄可以有多張（最多 4 張，正反面是常態），
而**用陣列索引定位會在刪掉中間一張時整排位移**——伺服器上那張就變成永遠清不掉的孤兒。
照片有自己的 id，刪除這件事在任何一端都不會算錯。

推送紀錄時一併帶 `photoIds: ["7d31…", …]`。**伺服器必須刪掉該紀錄名下、但不在
`photoIds` 裡的照片**：這就是「移除一張名片」的表達方式。刻意不另設刪除端點，理由與
墓碑那節相同——一個「要記得呼叫」的端點，正是這些檔案最後永遠留著的原因。

> 判斷該刪哪些時，`photoIds` 要從**伺服器上既有的那一份**讀，不是只看送進來的這一份：
> 墓碑根本不帶 `photoIds`，只看新的會什麼都刪不掉。

**照片刻意不走紀錄的 JSON。** 壓縮後單張 200–500KB，100 筆就是 20–50MB。在斷斷續續的
Wi-Fi 下，把照片和紀錄綁在同一個請求裡代表：照片傳失敗會連帶讓紀錄也重傳，永遠傳不完。
分開之後，紀錄先到（那是真正重要的資料），照片可以慢慢補、單獨重試。

**照片只有單向。** 拉取回應不含照片，所以另一台平板拉到的紀錄不會有圖。v2 之後跨平板
互看已經成立（活動會同步了），但照片仍然只上不下——實作者不必為拉取準備夾帶影像的路徑。
理由是頻寬：把每張名片都散佈到每一台平板，換來的只是在小螢幕上看一眼，而完整的照片在
伺服器上、也在匯出檔裡。

客戶端只替**伺服器已經接受過**的紀錄上傳照片，並以照片內容的摘要判斷是否需要重傳——
改個錯字不會讓一張 500KB 的圖再飛一次。摘要是**逐張**記的，所以一筆紀錄裡換掉其中一張，
只有那一張會重傳。

## 衝突處理

**Last-write-wins，比 `updatedAt`；相同時比 `deviceId` 字串大小**（純粹為了讓兩邊
算出同樣的贏家，沒有其他意義）。

> **本機的每一次修改都必須把 `updatedAt` 蓋過它所修改的那個值**，不能只是取「現在」。
> 平板的時鐘會走偏：從一台快 10 秒的平板拉來的紀錄，其 `updatedAt` 可能還在未來，
> 這時用當下時間標記的刪除會比被刪的東西還「舊」，同步就把它丟掉——**刪除靜靜地沒有生效，
> 而且哪裡都不會報錯**。客戶端的 `nextUpdatedAt()` 就是在處理這件事，
> `tests/e2e-sync.js` 有一條刻意製造時鐘偏差的斷言守著。

> **LWW 對「未來的時間戳」沒有防禦。** 一台時鐘設在 2099 年的裝置送出的紀錄，
> 會贏過此後每一次合法修改，而且沒有任何錯誤訊息——那筆資料等於被凍結了。
> 這與上一段的時鐘偏差是同一個家族的問題，只是嚴重得多。
> 客戶端不做這件事（`nextUpdatedAt()` 只在必要時 +1ms），但**伺服器如果要防，
> 唯一可靠的辦法是拒收 `updatedAt` 超過伺服器現在時間某個容忍值（例如 5 分鐘）的資料**，
> 因為只有伺服器有一個可信的時鐘。參考實作刻意不做——它是規格，不是防線——
> 但正式伺服器應該做。
>
> （這一條是寫測試時撞出來的：`tests/e2e-event-sync.js` 早期版本用 2099 年的
> `updatedAt` 去試探擁有者規則，結果讓那場活動再也接受不了任何真實的修改，
> 後面四條斷言全紅。要花力氣才找得到原因，正是因為它不會報錯。）

**這個規則會丟掉一次編輯。** 如果兩台平板都改了同一筆而且都還沒同步，較早的那次修改
會被覆蓋且無法復原。接受的理由是：每筆紀錄由某一台平板建立，實務上也只有那台會編輯它
——接待人員修的是自己剛才填錯的東西。跨裝置同時編輯同一位訪客，在這個流程裡幾乎不會發生。

如果日後這個假設不成立（例如加了集中式的資料整理介面），這一條要重新設計，不要
硬撐 LWW。

### 墓碑

刪除是 `deletedAt` 非 null 的紀錄，一樣參與 LWW。伺服器**必須保留墓碑**，否則已刪除的
紀錄會從還沒同步的平板上重新長回來。

客戶端的墓碑只保留 `id` / `eventId` / `deviceId` / `timestamp` / `updatedAt` / `deletedAt`，
**所有欄位值與照片都已丟棄**——已刪除的紀錄不該還在平板上留著訪客的姓名、電話與名片照。

> **收到墓碑時，伺服器必須一併刪除該紀錄的所有照片。** 上面那句話的理由不會因為換到伺服器
> 這一端就失效。刻意不另設刪除端點：刪除已經由紀錄本身表達了，而一個「要記得呼叫」的
> 端點，正是這些檔案最後永遠留著的原因。

伺服器確認收到之後，客戶端可以清除本機墓碑。清除多久之後才安全，取決於「一台平板可能
多久沒上線」，建議至少保留一次展覽的長度。

**活動也有墓碑，理由一模一樣。** 活動一旦會同步，硬刪除就壞了——下一次拉取會把它整個
長回來。收到活動墓碑時，伺服器**必須一併刪除該活動底下所有紀錄的照片**，理由與紀錄墓碑
相同。客戶端則連同該活動的欄位定義一起刪除（定義不是需要保留的東西，紀錄才是）。

## 欄位定義的擁有者

每場活動記一個 `ownerDeviceId`，預設是建立它的那台平板。**只有擁有者能改欄位定義**，
其他平板的「表單管理」三個欄位頁籤是唯讀的（資料紀錄與匯出不受影響——任何平板都照常收單）。
管理模式的活動卡片上有「接管欄位設定」，一層確認，接管即把 `ownerDeviceId` 指向本機
並推進 `updatedAt`，靠 LWW 傳播出去。

**這樣做是為了讓欄位定義完全不需要合併。** 定義是一個巢狀結構——欄位裡有選項清單、
有排序——兩個人各加一個選項要怎麼合，沒有正確答案，只有幾種都會讓人失望的猜測。
指定一個擁有者，衝突就從源頭消失了。

> **這和後台 PIN 一樣是防誤觸，不是權限控制。** 在共用權杖的前提下，伺服器分不出
> 「刻意接管」和「冒名頂替」——接管本來就是合法動作，而它就是改 `ownerDeviceId`。
> 要防的是同事在自己平板上改了欄位、把大家的設定蓋掉這種意外。
> 真正的權限控制需要每台裝置各自的憑證，那是
> [#10](https://github.com/art20217/exhibition_form/issues/10) 的範圍。

## 個資與合規

**測試階段一律使用假資料。**

給訪客看的同意條文寫的是「本人資料不會提供予第三方」。上傳到**該公司自己的**伺服器
沒有問題（同一個資料控制者），但開發或測試用的伺服器**就是第三方**——把真實訪客資料
送上去會直接違反平板上剛給對方看過的那段文字。

同步一旦上線，安全性與合規（[#10](https://github.com/art20217/exhibition_form/issues/10)）
就不再是可以延後的項目：資料離開裝置的那一刻，「PIN 只防誤觸」會從已知限制變成真正的問題。

## 給實作者的檢查清單

- [ ] 同一批資料送兩次，結果與送一次相同（冪等）
- [ ] `seq` 單調遞增，且不因伺服器重啟而倒退
- [ ] 活動與紀錄各有各的 `seq`，互不干擾
- [ ] 墓碑會被保留並回傳給拉取端（紀錄與活動都是）
- [ ] 一筆壞資料不會讓整批失敗
- [ ] 照片端點與紀錄端點可以獨立失敗與重試
- [ ] **收到紀錄墓碑時刪掉該紀錄的所有照片**（否則已刪除訪客的名片照會永久留存）
- [ ] 紀錄不再列出的照片會被刪掉（`photoIds` 修剪），且判斷時讀的是伺服器上既有的那一份
- [ ] **收到活動墓碑時刪掉該活動底下所有紀錄的照片**
- [ ] 非擁有者送來的 `fieldDefs` 被拒收，但活動本身仍收下
- [ ] `updatedAt` 遠超過伺服器現在時間的資料被拒收（否則一次時鐘錯誤可以永久凍結一筆資料）
- [ ] 認證失敗回 401，不要回 200 加錯誤訊息（客戶端要能區分「網路壞了」和「憑證錯了」）
- [ ] **`OPTIONS` 在路由與認證之前就回答**，未實作的路徑也一樣（否則預檢被擋，客戶端只會看到「網路錯誤」）
- [ ] 每個請求都寫一行 log（狀態碼、方法、路徑）——現場唯一能回答「哪一個請求失敗」的地方
